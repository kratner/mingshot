# M0 spike: results (2026-11-26)

M0 (PLAN.md §6): New button / ⌃⇧2 → overlay → frozen frame → region → PNG on the clipboard, Mac only. Measured on
an M5 MacBook with three displays: built-in at 2048×1280 @1×, a 1920×1080 @1×, and a 4K @2× (1920×1080 pt). The
machine was busy throughout: RustDesk streaming the screen, a VM and Docker running (load average 4–11).

## How it works

- **Capture:** ScreenCaptureKit `captureImageInRect` (macOS 15.2+), one call per display, all in parallel. It reads
  the same composited picture as the Mac's full-screen screenshot, so window edges and glass effects come out
  exactly as on screen.
  - Tried first and dropped: ScreenCaptureKit's content-filter captures (`SCContentFilter`, and macOS 26's
    `captureScreenshotWithFilter`). They can leave MingShot's own windows out, but they also drop the light edge
    lines macOS draws around windows (up to 219 levels off on window borders).
- **Keeping MingShot out of the picture:** every MingShot window is marked not shareable
  (`NSWindowSharingNone`) while the displays are read, and `captureImageInRect` leaves such windows out. The capture
  window is also ordered out with its animation off (with the animation, the shrinking window was caught in 5 of 30
  runs). Once all frames are in, the windows are shareable again, so RustDesk and screen sharing see the overlay.
- **Overlay:** goes up the instant New is clicked, before the screen is read: a transparent Tauri webview per display
  (dimming, crosshair, selection, size). Under it, a native window per display shows the frozen CGImage in a layer
  (no encoding, no copy into the webview) as each display's frame arrives, so the display under the pointer never
  waits for a slower one.
- **Crop:** the selection (points, snapped to device pixels in the page) is converted to the frame's pixels by its
  own pixels-per-point, cropped with `CGImageCreateWithImageInRect`, encoded as PNG by ImageIO with the display's
  colour profile, and put on the clipboard as the only item (image only, §7.8).

## Results

| Check | Result |
|---|---|
| Whole-display frames vs `screencapture -D` (`npm run selftest`) | **Exact** on all three displays (1× and 2×); pixels animating between the before/after screenshots are counted, not compared |
| Regions (ordinary, odd coordinates, far corner) vs `screencapture -D` | **Exact**, 9 of 9 |
| End to end: real ⌃⇧2 → overlay → selection → clipboard PNG vs the screen (`npm run e2e`) | **Identical** on all three displays; Esc cancels and leaves the clipboard alone |
| MingShot's capture window in a frame (bench, positive control finds ~39,500 px) | **0 of 50** runs |
| Overlay in a frame (bench paints it opaque magenta) | **0.00%** of any display |
| New → overlay up | median **19 ms**, p90 26 ms (after the stall fix below) |
| New → pointer's display frozen under it | median **62 ms**, p90 87 ms (after the fix; 58–165 ms medians before it, depending on load) |
| New → every display frozen | median 120 ms, p90 146 ms |
| Window-server pauses (overlay and capture both held ~500 ms) | 1 in 30 runs, under heavy load |

`screencapture -R` (the ⌘⇧4 path) is not used as the strict reference: it differs from the screen itself by 1–11
levels over glass and blur materials (desktop widgets, wallpaper). MingShot matches the screen; the e2e and
self-test report the `-R` difference for information.

## Open

1. **The mouse drag needs a hand check.** Synthetic mouse drags don't reach WebKit on this Mac (a plain page in
   Safari didn't see them either), so the e2e test makes the selection through the same code a mouse release runs
   (`MINGSHOT_E2E_SELECT`). Keith: click New, drag a region on each display, paste into Preview.
2. **Occasional 500 ms pause, mostly fixed.** `CATransaction::flush()` after showing the overlay sometimes took almost
   exactly 500 ms (4 in 30 runs). Fixes, in order of effect:
   - The overlay is flushed to the screen *before* MingShot activates itself (activation is a handshake with the
     previously active app). This brought it to 1 in 30.
   - The overlay windows' fixed settings (not shareable, level, Spaces, no animation, not movable) are applied
     while they're hidden, not on New's path.
   - Between captures the overlays stay on screen fully transparent and click-through instead of being ordered
     out (no measurable effect on its own, kept as harmless).
   The remaining case is the window server pausing: that run's capture was held up by the same ~500 ms. It was
   seen with RustDesk streaming the screen; worth re-measuring with RustDesk off. Logged as `slow show_ui` in
   ~/Library/Logs/MingShot/mingshot.log.
